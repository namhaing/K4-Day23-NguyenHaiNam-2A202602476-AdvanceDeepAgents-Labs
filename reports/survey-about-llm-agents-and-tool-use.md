# LLM Agents and Tool Use: Methods, Evidence, and Evaluation

## TL;DR

- LLM agents turn model outputs into actions against APIs, tools, or environments; the central design choice is how reasoning, action selection, external feedback, and planning are coupled. ReAct interleaves reasoning with actions, while Toolformer learns when and how to invoke APIs and Reflexion uses text feedback and memory across attempts. [1][2][3]
- Tool use has moved from a handful of APIs to catalog-scale settings: API-Bank evaluates 73 tools across 314 annotated dialogues, while ToolLLM targets more than 16,000 real-world APIs and pairs data generation with retrieval and decision-tree methods. [4][5]
- Strong aggregate task performance can conceal weak grounding and inconsistency: AgentBoard’s progress-rate metric tracks intermediate subgoals, while τ-bench reports GPT-4o success on fewer than half of tasks and pass^8 below 25% in retail. [6][7]
- Realistic deployment requires evaluation of security, cost and adaptation as well as success: AgentDojo measures utility under prompt injection, and CostBench finds GPT-5 below 75% exact match in the hardest static tasks and 34.91% in its cost-change setting. [8][9]

## Background

An LLM agent is not merely a language model that answers a prompt: it is a system that selects actions and interacts with an external environment, where tools can return information or cause changes to state. A review of agent paradigms organizes systems around environment and task, model roles, and workflow; it distinguishes tool use, planning, and feedback learning as related but distinct elements. [10] This distinction matters because an apparent “reasoning” failure may instead be an invalid tool choice, an incorrect argument, a misread result, or poor replanning after the environment changes. The evaluation literature accordingly separates behavioral objectives such as capability, reliability and safety from process choices such as interaction mode, benchmark, metric and context. [11]

The field’s foundational shift was from treating reasoning as text alone to testing action-and-observation loops. ReAct (2022) interleaves verbal reasoning traces with environment-facing actions: reasoning can track plans and exceptions, while actions obtain external information. Its studies span HotpotQA and Fever with a Wikipedia API, and embodied/web tasks ALFWorld and WebShop; with one or two in-context examples, it exceeded imitation- or reinforcement-learning baselines by 34 and 10 absolute success-rate points on ALFWorld and WebShop respectively. [1] Toolformer (2023) instead learns to decide which API to call, when, and with what arguments, using a self-supervised approach requiring only a handful of demonstrations per API. [2] These set up the enduring trade-off: explicit, inspectable reasoning-action traces versus learning invocation behavior as part of model prediction.

## From reasoning loops to learned tool policies

ReAct is a prompting-and-control pattern: it exposes intermediate reasoning and tool actions in a trajectory, and its reported gains used only one or two demonstrations on ALFWorld and WebShop. Toolformer is a training approach: it uses API-call decisions and tool results to improve zero-shot task performance, evaluating a calculator, QA system, search engines, translation and calendar tools. [1][2] As a result, the two works provide different kinds of evidence. ReAct reports task success comparisons on interactive environments; Toolformer reports broad zero-shot improvement across downstream tasks, often competitive with larger models, but its summary gives no comparable numerical success-rate table. [2]

A third axis is learning across attempts. Reflexion stores verbal reflections about task feedback in an episodic memory buffer rather than updating model weights; feedback can be scalar or free-form language and may be external or internally simulated. It reports 91% pass@1 on HumanEval, compared with 80% for the then-state-of-the-art GPT-4 as reported in the abstract. [3] Unlike ReAct’s within-trajectory reasoning or Toolformer’s learned API policy, Reflexion uses experience from prior trials to guide later ones. Planning surveys broaden the taxonomy to task decomposition, choosing among plans, external-module-aided planning, reflection/refinement, and memory-aided planning; they caution that textual reflection can support correction but does not guarantee reaching the goal. [12] These strategies should therefore be compared on where feedback enters—during a single action loop, in learned invocation behavior, or between attempts—not collapsed under the vague label “reasoning.”

## Scaling the tool interface and orchestration

A practical agent must map a user request onto the right tool, arguments and sequence. API-Bank makes that interface concrete with 73 API tools and 314 annotated tool-use dialogues in a runnable benchmark. [4] ToolLLM shifts the scale: it targets over 16,000 real-world APIs and combines a data set, an efficient decision tree, automatic evaluation and neural API retrieval. [5] The contrast is between controlled, relatively bounded tool interaction and retrieval/orchestration over a far larger catalog. Neither count alone establishes robust execution, but catalog size makes tool discovery and selection explicit system components rather than incidental prompt details.

Tool-learning work in 2024 further explores specialization and staged selection. GRANITE-20B-FUNCTIONCALLING introduces function-calling ability through multi-task learning of granular tasks, while ToolACE creates diverse function-calling training data through a self-evolution synthesis process and targets models with limited parameters. [13][14] Tool-Planner organizes tools into toolkits and uses tool clustering with dynamic solution-tree planning; SEER (2025) adds a dynamic experience pool and stepwise retrieval to support multi-step tool use. [15][16] These methods differ from API-scale retrieval: granular supervised tasks emphasize learning call behavior, whereas planning, clustering and experience retrieval emphasize selecting and sequencing available capabilities at inference. The HF summaries report these methodological aims but provide no common benchmark scores, so they do not establish which approach is more accurate or efficient. [13][15][14][16]

Recent work also treats collaboration and additional inference compute as means of solving harder tasks. MACT proposes multi-agent collaboration with tool use for online planning in complex table question answering, motivated in part by data cost and closed-source accessibility/reproducibility concerns; its retrieved abstract supplies no numerical comparison. [17] A 2025 study of test-time scaling reports gains from parallel sampling, sequential revision, verification and greater rollout diversity, but the summary does not name benchmark scores or compute costs. [18] These results suggest two different resource strategies—more coordinated agents or more inference-time search—but the available evidence does not quantify their relative benefit per unit cost.

## What agent benchmarks measure—and miss

Benchmarks increasingly move from static question answering toward multi-turn interaction and observable environment state. AgentBoard introduces progress rate to measure intermediate subgoals alongside grounding accuracy and trajectories, making evaluation more diagnostic than final success alone. [6] τ-bench evaluates dynamic exchanges with a simulated user, domain APIs and policy guidelines, grading final database state against an annotated goal; it also introduces pass^k to test repeat-trial consistency. Its abstract reports GPT-4o success on fewer than half of tasks and pass^8 below 25% in retail, showing that repeat-trial reliability can be substantially lower than a one-run result. [7] Together these benchmarks show that progress, grounding, state correctness and consistency are distinct measurements, not interchangeable proxies.

Tool benchmarks must also test difficult tool-mediated domains and imperfect instructions. API-Bank’s runnable tool system and annotated dialogues support repeatable evaluation of tool usage. [4] FEABench extends the setting to natural-language multiphysics tasks requiring operation of COMSOL Multiphysics, although the retrieved abstract provides no scores or task count. [19] Learning to Ask studies unclear instructions, analyzes real-world instructions and error patterns, and builds a benchmark for tool use under imperfect instructions, likewise without a quantified score in the available abstract. [20] These directions broaden what “tool competence” means—from selecting a function in a clean prompt to operating specialist software or recognizing ambiguity before acting—but reported benchmark existence should not be confused with demonstrated improvements.

## Reliability, security, and operational cost

Tool outputs and actions create failure modes not captured by answer accuracy. AgentDojo provides a stateful environment with 97 realistic tasks and 629 security test cases for evaluating prompt-injection attacks and defenses; it uses checks over final environment state to assess agent behavior. [8] This style of evaluation makes security and utility measurable in an interactive setting, while the available spot-check of the abstract does not support broader numerical claims about attack success or defense effectiveness. [8]

Reliability also depends on whether an agent can recover from tool errors, adapt to changing conditions and control resource use. CRITICTOOL is a 2025 benchmark focused on self-critique in tool-calling error scenarios, though the HF summary provides no measured scores. [21] CostBench explicitly evaluates multi-turn cost-optimal planning with changing tool costs, availability and user preferences; its reported best model, GPT-5, remains below 75% exact match on the hardest static tasks, with substantial degradation under dynamic cost changes. It measures cost gaps and invalid tool use in addition to task completion, addressing a limitation of success-only benchmarks. [9] The comparison between τ-bench and CostBench is instructive: repeated success tests consistency, whereas dynamic cost changes test whether an agent notices a changed world and replans. [7][9]

## Trends and open problems

In the last two years, research has expanded from tool selection and single-run success toward longer interactive tasks, realistic state changes, multimodal or specialized tools, security and efficiency. Recent examples include Fara-7B for computer use, Agent0-VL for tool-integrated vision-language reasoning, tool-error self-critique, and benchmarks for unclear instructions and multiphysics software. [20][19][21][22][23] The notes provide few comparable numbers for these new approaches; claims such as Fara-7B outperforming larger models or self-evolution improving performance are not accompanied in the retrieved summaries by benchmark names and scores. [14][23] The evidence therefore supports an expansion of research targets more strongly than a general claim that agents have become reliably competent.

Three gaps stand out. First, evaluations need reproducible, state-based measures that combine final completion with intermediate progress, tool-selection/grounding accuracy, consistency across repeated trials, and adaptation to user or environment changes. [6][11][7][9] Second, safety testing must remain dynamic: AgentDojo’s differences across Slack and travel scenarios and its call for extensible evaluation show that security cannot be inferred from average benign performance. [8] Third, performance should be reported with operational cost and failure analysis. Existing summaries often omit token/runtime costs, benchmark sizes or direct comparative scores, making it difficult to determine whether multi-agent coordination, test-time scaling, retrieval or fine-tuning is the more efficient path. [17][18] The open problem is not simply to make an agent call tools more often; it is to make tool use selective, grounded, recoverable, secure and economical across multi-step environments, and to measure those properties on shared, changing benchmarks. [11][8][9]
